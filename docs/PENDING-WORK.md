## P0 — Blocks store submission

### 1. Deep-link verification files are unedited placeholders

Both platforms. App Links / Universal Links **do not work today** — links open
in the browser instead of the app.

| File | Current content |
|---|---|
| `public/.well-known/apple-app-site-association` | `"appIDs": ["TEAMID.com.askchetnam.app"]` — literal `TEAMID`, twice |
| `public/.well-known/assetlinks.json` | `REPLACE_WITH_UPLOAD_KEY_SHA256`, `REPLACE_WITH_PLAY_APP_SIGNING_SHA256` |

- iOS: replace `TEAMID` with the 10-character Apple Team ID (both occurrences).
- Android: two fingerprints are needed — your **upload key** SHA-256 *and*
  **Play App Signing** SHA-256 from the Play Console. Using only the upload key
  is the usual reason this silently fails after Play re-signs the bundle.

### 2. iOS has no entitlements file at all

`find mobile/ios -name '*.entitlements'` returns nothing. Capacitor generates
the Xcode project without one, so these capabilities are **not configured**:

- **Sign in with Apple** — required by App Store guideline 4.8 while Google
  sign-in exists. Missing this is a rejection, not a warning.
- **Push Notifications** (`aps-environment`) — `UIBackgroundModes` is set in
  `Info.plist`, but without the entitlement APNs registration fails at runtime.
- **Associated Domains** (`applinks:askchetna.com`) — needed for item 1 to work
  even once the AASA file is correct.

Added in Xcode under Signing & Capabilities, then committed.

### 3. iOS `Info.plist` has no `CFBundleURLTypes`

Verified: zero occurrences of `CFBundleURLTypes` or `REVERSED_CLIENT_ID`.
Firebase phone auth and Google sign-in both hand control to a URL callback on
iOS; without the reversed client ID scheme registered, the flow cannot return to
the app. Value comes from `GoogleService-Info.plist`.

### 4. Native version numbers never left 1.0

| | Value | Web package |
|---|---|---|
| `mobile/android/app/build.gradle` | `versionCode 1`, `versionName "1.0"` | 2.1.8 |
| `mobile/ios/.../project.pbxproj` | `MARKETING_VERSION = 1.0`, `CURRENT_PROJECT_VERSION = 1` | 2.1.8 |

Both release workflows accept an override input (`versionCode`/`versionName` for
Android, `buildNumber` for iOS), so CI can supply these — but the committed
defaults are wrong, and **Play rejects any upload whose `versionCode` does not
increase**. Decide whether the workflows always pass an override or the files
get bumped; today it is neither.

### 5. Phone OTP fails for real numbers — Firebase on Spark

Confirmed `BILLING_NOT_ENABLED` (28 Jul). Real SMS is billable and the Spark
plan blocks it; test numbers work because they never send an SMS. **Fix is to
upgrade to Blaze** — no code change, no rebuild.

Before going live on Blaze: real SMS exposes you to SMS-pumping fraud. Tighten
the SMS region allow-list to India only (remove Indonesia after testing), set a
Google Cloud budget alert, and enable App Check.

## P1 — Web

### Light-theme gold fails WCAG AA as text — site-wide

Measured, not estimated:

| Pair | Ratio | AA normal text (4.5) |
|---|---|---|
| `--accent-gold` `#B8860B` on `#FDF4E3` | **2.98** | fails |
| `--accent-gold-dim` `#996515` on `#FDF4E3` | 4.55 | passes |
| `--accent-gold` `#D4AF37` on `#0B0F2F` (dark) | 8.89 | passes comfortably |

Gold is used for body-weight text in many places — labels, inline emphasis,
link text. In dark mode it is fine; in light mode it is roughly two-thirds of
the required contrast. `--accent-gold-dim` already exists and already passes, so
the fix is to route *text* uses through it in light mode while `--accent-gold`
stays the decorative/border colour.

Not done here because it changes the look of every light-mode screen and wants a
deliberate design pass rather than a find-and-replace.

### Light theme is broken on 7 surfaces

These files hardcode `#0B0F2F` / `#DFE0FF` instead of using theme variables, so
they stay dark when the user picks the light theme:

**Fixed in 2.1.9** — `PendingDeletionGate`, `app-info`, `offline` and
`debug/version` now read theme variables. `--warning`, `--accent-iris` and
`--brand-secondary` also gained light-mode values; they existed only under
`[data-theme='dark']`, which is *why* those screens hardcoded dark hexes.

Remaining, and all three are arguably correct as-is:

```
src/app/layout.tsx           theme-colour meta tag — deliberate
src/components/Logo.tsx      brand mark — deliberate
src/components/NativeAppShell.tsx
```

`app-info` is now linked from the footer for signed-out users, so it is more
visible than it was. `PendingDeletionGate` matters most — it is a
compliance-critical screen a user may be staring at while deciding whether to
keep their account.

Some of these are deliberate (`layout.tsx` theme colour, `Logo.tsx` brand mark);
each needs a judgement call rather than a blanket fix.
