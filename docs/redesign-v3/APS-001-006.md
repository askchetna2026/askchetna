# Purpose

This section defines exactly what AskChetna is responsible for.

One of the biggest reasons software projects fail is because the product gradually expands beyond its original intent.

This section prevents uncontrolled scope expansion.

Every future feature request must first be validated against this document.

If it falls outside the approved scope, it must either:

- be rejected
- become a future roadmap item
- require a formal APS revision

---

# Product Definition

AskChetna is an AI-powered guidance platform designed to help users think more clearly through structured, trustworthy and beautifully designed digital experiences.

AskChetna assists users.

It does not replace their judgement.

# Product Responsibilities

The platform is responsible for:

Helping users organise thoughts.

Helping users learn.

Helping users reflect.

Helping users explore possibilities.

Helping users understand available information.

Helping users continue their personal journey.

Helping users discover relevant tools.

Helping users revisit previous sessions.

Providing a beautiful and trustworthy experience.

---

# Product Is NOT Responsible For

Making decisions for users.

Predicting the future with certainty.

Replacing professional advice.

Replacing doctors.

Replacing lawyers.

Replacing financial advisors.

Replacing therapists.

Making promises.

Creating dependency.

Manipulating emotions.

Creating addictive behaviour.

# Feature Qualification Rules

Before any new feature enters development it must satisfy the following questions.

---

FQ-001

Does the feature support the Product Mission?

---

FQ-002

Does the feature solve a documented user problem?

---

FQ-003

Can the feature reuse existing components?

---

FQ-004

Can the feature reuse the Design System?

---

FQ-005

Can the feature be implemented consistently across Web, Android and iOS?

---

FQ-006

Does the feature introduce unnecessary complexity?

---

FQ-007

Can the feature be maintained over the next five years?

---

FQ-008

Does the feature improve user trust?

---

If the answer to multiple questions is "No", the feature should not proceed.

# Product Boundaries

The following boundaries must never be crossed without APS revision.

Boundary B-001

No platform may create its own design language.

---

Boundary B-002

No platform may implement undocumented UX.

---

Boundary B-003

No feature may bypass the Component Library.

---

Boundary B-004

No page may ignore the Design Token System.

---

Boundary B-005

No AI coding assistant may invent UI patterns.

---

Boundary B-006

No visual identity may diverge from the approved Asset Bible.

---

Boundary B-007

No engineering shortcut may permanently violate APS.
